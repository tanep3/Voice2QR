# Voice2QR システム設計

Voice2QR 全体の構成と、各部の接続の設計。正本は要件文書
`docs/requirements.md`、データ形式は `docs/format.md`、コアの API は
`docs/core-api.md`。本書はその下で「部品をどう組み、データがどう流れ、
どうビルドして配るか」を定める。

ステータス： 凍結（2026-11-14、レビュー済み）。変更は版を上げて行う。

## 1. 全体像

```
  顔（利用者）
  ┌─────────────┬───────────┬────────────────┬──────────────┐
  │ Web アプリ   │ CLI       │ 他人の Web アプリ │ Android アプリ │
  │ (TypeScript)│ (Node)    │ (JS)            │ (Kotlin)      │
  └──────┬──────┴─────┬─────┴───────┬────────┘               │
         └─────────────┴─────────────┘                        │ C ABI (JNI)
                      │ JS API（版付きの公開面）                │
  ┌───────────────────┴──────────────────┐                   │
  │ JS ライブラリ (TypeScript)             │                   │
  │ 高水準 API / bridge / QR 生成・読取    │                   │
  └───────────────────┬──────────────────┘                   │
                      │ C ABI（wasm）                         │
  ┌───────────────────┴──────────────────────────────────────┴─┐
  │ 共通コア voice2qr-core (Rust)                                │
  │ qv 層（形式） / codec 層（抽象） / engine 層                  │
  └───────────────────────────┬──────────────────────────────────┘
                              │ 動的リンク（別ファイル / 別 .so / 別 wasm）
  ┌───────────────────────────┴──────────────────────────────────┐
  │ Codec2 (LGPL-2.1、無改造、バージョン固定 §6)                   │
  └──────────────────────────────────────────────────────────────┘
```

設計の要点：

- コアは1つだけ。JS ライブラリがコア（C ABI）の上に乗り、
  Web アプリ・CLI・他人の Web アプリはライブラリの公開 API に
  対して実装する。C ABI を直接使うのは JS ライブラリと
  Android だけである。JS ライブラリは「顔」ではなく「層」である。
- QR の生成・読取はコアの外（§2.3）。コアの出入り口は PCM と
  QV ペイロードバイト列のみ。
- 公開版の Web アプリはサーバ処理を持たない（静的配信のみ）。
  他人の Web アプリからは、Pages 上の JS ライブラリとして
  利用できる（§4.1）。HTTP API サーバは作らない。

## 2. Web アプリ（最初の顔）

### 2.1 技術構成

- 言語： TypeScript（素の DOM 操作。フレームワークは使わない —
  画面が少なく、部品の差し替え可能性を優先する）
- ビルド： Vite
- 配置： 静的ファイル一式。公式ビルドは GitHub Pages（§7）。
  同じサイトに、アプリ本体・JS ライブラリ（§4.1）・使い方の
  案内ページ（docs ページ）を同居させる
- アプリはライブラリを**バンドルに取り込まず**、同居する版付き
  ライブラリを相対パスで実行時に読み込む。アプリ自身が公開
  ライブラリの利用者になる（§4.1）

### 2.2 モジュール構成

```
web/
  lib/                 JS ライブラリ（§4.1）。DOM に依存しない
    index.ts           高水準 API（Promise ベース）の公開面
    bridge.ts          コア wasm の読み込みと型付きラッパ（C ABI の射影）
    qr-generate.ts     ペイロード → モジュール行列（Nayuki qrcodegen の TS 版）
    qr-read.ts         ピクセル列 → ペイロード（zxing-wasm）
    image-adapter.ts   画像の出し入れの抽象（環境差はここで吸収）
  app/                 Web アプリ本体（DOM を使う側）
    main.ts            起動、画面遷移（つくる / よむ）、言語の初期化
    recorder.ts        マイク録音（getUserMedia + AudioWorklet）
    file-import.ts     音声ファイルの取り込み（decodeAudioData → 8 kHz 化）
    player.ts          復号 PCM の再生（Web Audio）
    print.ts           印刷レイアウト（QR のみ、固定物理サイズ）
    settings.ts        言語、上級者設定（bps / 誤り訂正レベル）の保持
    i18n.ts            日英の文言辞書と切替
    sw.ts              Service Worker（PWA： 資産のキャッシュ）
```

ライブラリ（lib/）は DOM 非依存に保つ。CLI が Node から同じ部品を
使うためである（§4.2）。環境で変わるのは画像のピクセル化と
ファイル入出力だけで、その差は image-adapter で吸収する
（ブラウザ： canvas / ImageBitmap、Node： PNG デコーダ等）。

### 2.3 QR の扱い（コアの外）

- 生成： Nayuki の QR Code generator（TypeScript 版、MIT）で
  ペイロードからモジュール行列を得て、canvas に整数倍拡大で描く。
  保存 PNG も同じ描画から作る（補間なし）。
- 読取： zxing-wasm（MIT）。画像ファイルは ImageData 化して渡し、
  カメラは video からフレームを周期的に切り出して渡す。
- どちらも「バイト列 ⇔ QR」の変換だけを担い、QV の意味は知らない。

### 2.4 WASM の接続（LGPL 分離の実装形）

Web では部品が2つの wasm ファイルになる。

- `voice2qr_core.wasm`： コア。C ABI（`qv_*`）を export し、
  Codec2 の関数（`codec2_*`）を import する。
- `codec2.wasm`： 無改造の Codec2 C ソースから別途ビルドした
  モジュール。`codec2_*` を export する。

接続は JS 側の媒介で行う： codec2.wasm を先に実体化し、その export を
コアの import に渡す。フレームは6バイト、PCM の塊も小さいため、
モジュール境界でのコピー費用は無視できる。この形により「単一バイナリ
に一体化しない」という LGPL 上の分離（要件 §6）が、ファイル単位で
そのまま成立する。

ネイティブ（Android、テスト）では通常の動的リンク（別 .so）を
使うため、この媒介は Web だけの話である。

### 2.5 データの流れ

生成（マイク）：
マイク → AudioWorklet（端末レート → 8 kHz モノラル i16 に変換）→
bridge の符号化セッションへ push → 統計（フレーム数・ペイロード長）を
プログレスバーとカウントダウンに反映 → 停止で finalize →
ペイロード → QR 描画 / PNG 保存 / 印刷。

生成（ファイル取込）：
ファイル → decodeAudioData → ダウンミックス＋8 kHz 化 →
ワンショット符号化 → 以降は同じ。

読取・再生：
画像 / カメラ → zxing → ペイロード → inspect（観測： 音声の有無と
長さを表示）→ decode → PCM → 再生。

再生確認（生成直後のプレビュー）も、必ずペイロードを decode して
行う。符号化直後の PCM をそのまま鳴らすことはしない（QR に実際に入る
音と、確認で聞く音を同一にするため。要件 §4.1）。

### 2.6 データを保持しないことの担保

- PCM とペイロードはメモリ上のセッションオブジェクトだけが持ち、
  画面遷移・完了・リセットで破棄する。
- 永続化するのは設定（言語、bps、誤り訂正レベル）のみ
  （localStorage）。音声とペイロードはストレージに書かない。
- Service Worker がキャッシュするのはコード資産（HTML / JS / wasm）
  だけであり、利用者のデータは扱わない。

### 2.7 容量と設定

誤り訂正レベル → QR バイトモード容量（最大バージョン40）：
L = 2,953 / M = 2,331（標準）/ Q = 1,663 / H = 1,273。
上級者設定の bps と誤り訂正レベルから容量が決まり、それをコアの
`capacity` 引数に渡す。録音の上限時間はコアの `qv_max_duration_ms`
で算出してカウントダウンに使う（時間ではなく容量で止める）。

### 2.8 エラー処理

- コアのエラー種別（`docs/core-api.md` §3.2）のうち NotQv /
  NoVoiceSection / Malformed は、利用者には「読み取れませんでした」
  として一本化する。
- カメラ読取で QR が見つからない間はエラーにせず走査を続ける。
  ファイル読取で見つからない場合は「読み取れませんでした」。
- マイク許可の拒否、HTTPS でない環境での getUserMedia 不可などは、
  原因別の案内文を表示する。文言はすべて i18n 辞書を通す。

### 2.9 PWA と印刷

- PWA： manifest と Service Worker で「ホーム画面に追加」と
  オフライン動作（初回読み込み後はネットなしで起動）を提供する。
  レスポンシブデザインとし、スマートフォンのブラウザでも使える。
- 印刷： 印刷専用レイアウトで QR のみを固定物理サイズ（CSS の mm
  指定）で配置する。用紙幅から自動で決めない（要件 §4.2）。
  ブラウザ印刷でのモジュール再現性は未検証の宿題（要件 §8）。

## 3. Android アプリ（フェーズ2の概形）

- Kotlin ＋ JNI の薄いラッパで、コア（.so）と Codec2（別 .so）を叩く。
- 録音は AudioRecord、読取カメラは CameraX ＋ zxing-cpp、印刷は
  OS の共有で Phomemo アプリへ渡す。INTERNET 権限は持たない。
- applicationId は `work.tanep.voice2qr`（決定済み）。
- 詳細設計はフェーズ2の開始時に行う。本書では、Web 先行の実装が
  Android の前提（コア契約とデータ形式）を壊さないことだけを確認する。

## 4. JS ライブラリ（層）と CLI（顔）

### 4.1 JS ライブラリ（他人の Web アプリ向け）

「API 提供」はサーバではなく**ライブラリ配布**の形で行う
（2026-11-14、本人の意向を確認）。HTTP API サーバは作らない。
公開 API の設計は `docs/js-api.md` に置く。

- Web のビルド成果物には、アプリ本体とは別に、JS ライブラリ一式を
  含める： ES モジュール（`voice2qr.js`）＋型定義（`.d.ts`）＋
  2つの wasm（§2.4）。GitHub Pages 上の版付き URL で公開する
  （例： `/lib/v1/voice2qr.js`）。
- GitHub Pages は `Access-Control-Allow-Origin: *` を返すため、
  他のサイトの Web アプリからそのまま import して使える
  （2026-11-14 に実測で確認）。処理は利用側のブラウザ内で完結し、
  こちらのサーバ負荷は静的ファイルの配信だけである。
- ライブラリの公開面は高水準の Promise ベース API とする
  （PCM → ペイロード / QR、ペイロード → PCM、inspect）。
- 自分の Web アプリは、このライブラリの**最初の利用者**である。
  アプリはライブラリをバンドルに取り込まず、同居配置された
  版付きライブラリを相対パスで実行時に読み込んで使う。これにより
  公開物とアプリが同一物・同一手順になり、公開 API が腐らない。
  読み込み先は相対パスに限る（絶対 URL で本家へ取りに行くと、
  自宅配置のような自己完結すべき配置が外部に依存してしまう）。
  アプリは使うライブラリの版を固定し、版上げは意図的に行う。
- 使い方の案内ページ（docs ページ）を同じ Pages サイトに置く：
  import 方法、API 一覧、動作例、版の指定方法、Codec2 の
  ライセンス上の注意（ファイルを自前ホストする場合に必要な
  分離と帰属表示）。
- 注意： GitHub Pages には帯域のソフトリミットがあるため、
  利用が大きく育つ場合は jsDelivr 等の GitHub 連携 CDN へ
  移す（コードの変更は不要で、読み込み先 URL が変わるだけ）。

### 4.2 CLI（自分の自動化向け）

- CLI は **JS ライブラリを Node から呼ぶ薄い殻**とする
  （例： `voice2qr encode in.wav out.png`、`voice2qr decode in.png
  out.wav`）。コアの wasm は Node でもそのまま動くため、ネイティブ
  バインディングを別に作る必要がない。
- 前提は §2.2 の通り： ライブラリ本体を DOM 非依存に保ち、
  画像入出力だけを環境アダプタに寄せること。Node 側のアダプタは
  PNG の読み書き等を担当する。
- 利点： 自動化の結果が Web とバイト単位で同じになる（同じ wasm、
  同じライブラリを通るため）。シェルや cron、他の自前サーバ処理
  から叩ける。
- ライブラリが完成すれば薄く作れるため、フェーズ2を待たずに
  前倒ししてよい。

## 5. リポジトリ構成

```
core/                 Rust クレート voice2qr-core（include/qv.h を含む）
web/                  Web アプリ（TypeScript + Vite）
android/              Android アプリ（フェーズ2）
tools/                CLI（Node 製、JS ライブラリを呼ぶ）
codec2/               Codec2 の取得とビルドのスクリプト（§7）
docs/                 要件・形式・API・本書
fixtures/             ゴールデンテスト用データ（v2 で再生成）
spike/                2026-11-14 の方式検証コード（記録）
.github/workflows/    CI（§7）
```

## 6. ビルドと CI、リリース

- Codec2 は**バージョン 1.2.0 に固定**し、全ターゲット（ネイティブ
  テスト、wasm、Android）でソースからビルドする。理由： フィクスチャ
  は VM の libcodec2 1.2 系で生成されており、ゴールデンテストの
  バイト照合はエンコーダの版に依存する。配布環境のライブラリ版に
  引きずられないよう、版を固定して再現性を担保する。
- CI（GitHub Actions）：
  - コア： `cargo test`（ゴールデンテストを含む）を必須とする。
  - Web： 型検査とビルド。プレビューは置かない。
  - フィクスチャは CI で生成する。リポジトリに置くのはテキストの
    アンカー（`fixtures/expected/`： 決定的な合成信号に対する期待
    ペイロードの hex と復号 PCM の SHA-256）のみで、バイナリの
    フィクスチャは置かない。実音声のフィクスチャはローカルの
    証拠層として残し、無い環境ではそのテストをスキップする
    （ゴールデンテストの詳細はコア API 設計 §6）。
- リリース： バージョンタグ（SemVer）で起動し、Web バンドルを
  GitHub Pages へ配置する。APK の GitHub Releases 配布は
  フェーズ2で同じ仕組みに足す。
- 署名キー等の秘密情報は GitHub Secrets 経由とし、リポジトリに
  置かない（署名キーの生成と保管は本人の PC。要件 §6）。

## 7. 実装の順序

1. コア： qv 層と codec 層（libcodec2 接続）、ゴールデンテスト
2. コア： engine と C ABI、単体テスト
3. Web： bridge（wasm 接続）と生成系（録音 → QR → 保存）
4. Web： 読取系（画像 / カメラ → 再生）
5. Web： ファイル取込、印刷、i18n、PWA、JS ライブラリと docs ページ
6. CI と GitHub Pages リリース、実機確認（要件 §8 の宿題）
7. フェーズ2： Android（CLI は JS ライブラリ完成後に薄く作れるため前倒し可）

## 8. 未決・宿題

要件 §8 の検証項目（NDK ビルド、カメラ実機、M02S 印刷、ブラウザ印刷の
再現性）に加えて、本書時点の未決は次の通り。

- wasm の媒介接続（§2.4）が実ビルドで成立することの確認
  （コア実装の初期に小さく試す）。
- Codec2 1.2.0 のソース取得元とチェックサムの固定方法。
- Web のプレビュー再生と本再生で AudioContext の扱いを分けるか
  （実装時に判断）。
