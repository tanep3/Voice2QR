# Voice2QR 要件・決定事項

状態： 要件確定（2026-11-14）。開発は Muse が専用の VM で行い、コードと文書は GitHub コネクタ経由で tanep3/Voice2QR へ push する。この文書（`docs/requirements.md`）は Voice2QR の要件と決定事項の正本であり、用語と数値を自己完結で記す。Notion の同名ページは閲覧用コピー。

# 1. これは何か

- 本人の声そのものを QR コードに記録し、読み取ればネットワークなしでその場で再生できるアプリ／データフォーマット。
- 仕組み： 声 → Codec2 で符号化 → そのバイナリを QR コードのバイトモードに直接格納 → 読取時に Codec2 で復号して再生。
- Codec2 とは： 声を波形としてではなく「声の特徴パラメータ」として記録する音声コーデック（ボコーダ）。電話音声級の帯域で設計され、1,200 bps という極低レートでも本人の声として聞き取れる。オープンソースで特許フリー。
- テキスト＋読み上げ（TTS）方式は不採用。録った声をテキスト化した時点で、それは録音ではなく再演であり、本人の声は消えるため。
- 起点： 高校時代、「音をデータに変換すれば劣化せず保存できるはず」と考え、カセットテープへ A/D 変換記録を試みた Tane の体験。DAT（PCM）→ MP3 でも届かなかった 2,400 bps 級の帯域に、ボコーダなら声そのものが入る、というのが本プロジェクトの核。

# 2. 決定事項（方式）

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 音声コーデック | Codec2、**1200 bps** | 特許フリー・オープンソース。2400 bps は誤り訂正 M では約7.7秒で QR 容量を超過するため、紙用途では不採用 |
| QR 誤り訂正レベル | **M**（復元力 約15%） | 紙への印刷を前提に耐久性優先 |
| 記録時間 | 1個の QR で最大 **約15.5秒** | 誤り訂正 M のバイトモード容量 2,331 バイトから算出 |
| サンプリング | 8 kHz モノラル固定 | Codec2 の対象帯域 |
| データ形式 | QV フォーマット（§3） | PC／スマホ両アプリの共通契約 |
| QR 描画 | モジュール整数倍拡大、アンチエイリアスなし | 印刷時の再現性。補間してぼかさない |
| ネットワーク | 不使用（アプリ本体の静的配信を除く） | 全処理をクライアント端末内で完結させる。サーバは保存・変換・印刷を行わない |

# 3. QV フォーマット v1

詳細仕様は `docs/format.md`。ここでは要約のみ記す。

QR のバイトモードに以下をそのまま格納する。Base64 等のテキスト化はしない（容量が約33%無駄になる）。

- ヘッダ（3バイト）： magic "QV"（0x51 0x56）＋ version（現在は 2）。
- 本体はセクションの繰り返し（type 1バイト＋長さ 2バイト リトルエンディアン＋中身）。すべて可変長とし、読み手は未知のセクションを長さで読み飛ばす。
  - VOICE（0x01）： bps（2バイト）＋フレーム数（2バイト）＋ Codec2 フレーム列。1200 bps では 1フレーム = 40 ms = 6バイト。
  - TEXT（0x02）： UTF-8 テキスト。IMAGE（0x03）： 形式バイト（1 = WebP、2 = JPEG）＋画像バイト列。いずれも将来のマルチメディア形式用に予約し、Voice2QR は生成しない。
- Voice2QR の生成は VOICE のみ。読み取りはセクションを歩いて VOICE を取り出して再生する — 将来のマルチメディア QR でも、音声だけは Voice2QR で再生できる（2026-11-14 決定）。
- 復号手順： 先頭が "QV" でなければ Voice2QR データではない。VOICE セクションの bps とフレーム数でデコーダを初期化し、フレーム列を順に復号して 8 kHz PCM として再生する。VOICE が無い、または構造が壊れていれば「読み取れませんでした」と表示する。
- bps により他モードも同形式で格納できるが、印刷用途の標準は 1200 とする。
- 将来拡張： 15.5秒超は QR の Structured Append による連結。印刷は QR のみとし、人間可読テキストは併記しない（2026-11-14 決定。紙面を QR だけにして、再生時のサプライズを残すため）。
- v1（固定7バイトヘッダ）は 2026-11-14 のスパイクでのみ使われた未リリース形式であり、マルチメディア考慮のためリリース前に v2 へ置き換えた。

# 4. アプリ要件

構成は「1つのフォーマット＋1つのコア、顔が2つ」。先に作る顔は **Web**（2026-11-14 決定）。コア（QV の入出力と Codec2 への接続）は単一の共通実装とし、テストもコアに集中させる。両アプリはコアを呼ぶ薄い顔とする。コアの実装言語は Rust とし、C ABI を公開する（2026-11-14 決定）。コアの API 設計は `docs/core-api.md`、システム全体の設計は `docs/system-design.md` に置く。

## 4.1 両アプリ共通

- 機能： 録音、QR 生成、QR 読取、音声再生。
- QR 読取は2経路とも必須： (a) 画像ファイルからの読取、(b) カメラによるライブ読取。
- QR 出力は2経路とも必須： (a) 画面表示、(b) 画像ファイルとして保存。保存画像が印刷の原稿になるため、描画は整数倍拡大・補間なしで鮮明に。
- 録音データは保持しない（当面）。PCM は符号化のための一時データであり、QR 生成後に破棄する。保存物は QR 画像のみ。再生確認は QV ペイロードを復号して行う（QR に実際に入る音と同一にするため）。
- 入力はマイク録音と音声ファイル取込の両対応とする（ファイルは端末内で 8 kHz モノラルへ変換してから符号化する）。
- 生成パラメータは標準で 1200 bps／誤り訂正 M とし、上級者設定で変更可能とする。再生側は QV が持ちうる全 bps モードに対応する。
- UI の言語は日本語／英語を設定で切り替えられるようにし、初期値は端末の言語設定に従う。
- QV として読み取れない場合は「読み取れませんでした」と表示する。

## 4.2 PC アプリ（工房）— Web アプリ

- **全処理をブラウザ（クライアント）内で行う。サーバは静的ファイルの配信のみ**で、保存・変換・印刷をサーバ側では行わない。
- 録音／音声取込、QR 生成、QR 読取（画像ファイル＋Web カメラ）、再生をすべてブラウザ内で完結させる。マイク／カメラの利用には HTTPS 配信が前提（getUserMedia の secure context 要件）。
- 保存： ブラウザのダウンロード機能で QR 画像を保存する。
- 印刷： ブラウザの印刷機能を使う（印刷用レイアウトで QR を所定の物理サイズに配置する）。CUPS への直接印刷はしない。
- Codec2 は WebAssembly モジュールとして別ファイルで読み込み、LGPL 上の分離を保つ（§6）。
- アーカイブ管理はしない（§4.1）。利用者がダウンロードした QR 画像が保存物になる。
- 録音は最大約15.5秒で自動停止する。残り時間はプログレスバーとカウントダウンの両方で表示する。
- 対応ブラウザは Chrome 前提とする。
- 印刷は QR のみ（人間可読テキストは付けない）。印刷サイズは固定とし、用紙幅から自動で決めない（A4 などで巨大化するのを避ける）。
- フロントエンドの技術選定は Muse に一任（Tane 指示、2026-11-14）。
- 公式ビルドは GitHub Pages で配布する（リリース時に CI がビルドして配置）。各自がソースからビルドすることも可能とし、手順を公開する。
- PWA 化する（ホーム画面への追加、オフライン動作）。スマートフォンのブラウザでも使えるレスポンシブデザインとする。
- JS ライブラリとしても公開する： 他の Web アプリが GitHub Pages から import して使える形（ES モジュール＋型定義＋wasm、版付き URL）で、Voice2QR の Web 配信に含める。使い方を案内する docs ページを同じサイトに置く。自分の Web アプリも、その公開ライブラリを同居配置から相対パスで読み込んで使う（アプリはライブラリの最初の利用者であり、バンドルには取り込まない）。API の設計は `docs/js-api.md` に置く。
- 設定パネルはタブ連動（2026-11-19 決定）： 設定は両画面共通の1パネルだが、項目はタブごとに絞る。作る側の項目（ビットレート、誤り訂正、自動ゲイン）は「つくる」タブでのみ表示し、「よむ」タブでは言語のみ表示する。作る側の設定が読む側に出ているのは混乱の元、という指摘による。
- 読取画面の導線（2026-11-19 決定）： 再生ボタンは未読時は非表示とし、読み取り成功の瞬間に主役（primary・幅いっぱい）として現れる。再生中は停止ボタンに切り替わり、位置と目立ち方は維持する。
- 自動ゲイン調整（2026-11-19 決定）： 録音時の音量が小さいと再生も小さい問題への対策として、符号化前に録音全体のピークへ一括で合わせる正規化を行う。方式は実時間 AGC ではなく全体一括（最長約15.5秒と短いため可能）——ゲインが一定なので無音部分だけノイズが浮くことやポンピングは起きず、SNR は変わらない。目標ピークは約 -1 dBFS、増幅の上限は +30 dB（無音同然の録音を持ち上げすぎない）。ON/OFF は設定内のチェックボックスで切り替え、既定は ON。ON のときは録音をバッファして確定時に一括符号化し、OFF のときは従来のストリーミング符号化を使う。音声ファイル取込にも同じ設定が効く。
- 読取画面の「救出 QR」（2026-11-19 決定）： 読み取り成功時、読み取った生ペイロードを**元の誤り訂正レベル**で再エンコードした清浄な QR を、メインパネルの下・設定の上に表示し、PNG 保存と共有（Phomemo アプリへ送って即印刷できる経路を含む）を付ける。同レベル＝同容量のため容量超過は起こらない。用途は、薄汚れて消えかけた印刷 QR を「まだ読めるうちに」複製すること。復号に成功した時点でペイロードはビット単位で完全に復元されているため、再生成は劣化のない複製になる。

## 4.3 スマホアプリ（現場の機械）

- **完全スタンドアロン。ネットワーク機能を持たない。** 録音・符号化・生成・読取・復号・再生のすべてを端末内で行う。Android では INTERNET 権限なしで実装できる想定（必要な権限はマイク、カメラ、写真のみ）。
- 印刷はアプリ内に実装せず、OS の共有機能で QR 画像を Phomemo アプリへ渡す方式を第一とする。
- 読取： カメラ＋保存済み画像。
- 実装は Kotlin ＋ NDK/JNI で Codec2 の .so を叩く。対象バージョンは広く使われている範囲をカバーする（minSdk 26 / Android 8.0 を想定）。targetSdk は Google Play の最新要件に合わせる。
- 配布は二本立て： GitHub Releases で無料の自己責任バージョン、Google Play で有償版（§6）。ただし Play 配布は後付け（フェーズ2）とし、GitHub 版を先行させる。
- applicationId（パッケージ名）は `work.tanep.voice2qr` とする（2026-11-14 決定。所有ドメイン tanep.work の逆ドメイン記法）。後から変更しない。

# 5. 印刷ガイドライン

- 目安： 1モジュールあたり **3ドット以上**。
- 印刷レイアウトの基準幅は T02（48 mm 級）とする。一般印刷（A4 等）も許す。開発者の実使用は M02S を想定。
- 標準ケース（1200 bps、8.6秒、訂正 M）は QR バージョン30、クワイエットゾーン込み145モジュール。
  - M02S（300 dpi、53 mm幅 ≒ 626ドット）： 約4.3ドット／モジュール
  - T02（203 dpi、384ドット）： 約2.7ドット／モジュール
- クワイエットゾーン（周囲4モジュール）を必ず確保する。
- Web 版の印刷はブラウザ印刷に委ねるため、実効の再現性は OS／プリンタ側の画像処理に依存する。上のドット数は直接印刷時の目安であり、ブラウザ印刷での実測は §8 の宿題とする。

# 6. ライセンスと運用

- 配布： GitHub（tanep3/Voice2QR）で **MIT**。配布モデルは二本立てで、GitHub では無料の自己責任バージョンを配布し、スマホアプリは Google Play で有償販売する（事業目的あり。2026-11-14 に方針変更）。機能は無料版と同一とし、有償版が提供するのは導入と更新の手軽さである。Play 配布はフェーズ2として後付けし、GitHub 版を先行させる。自前コードの著作権表示は「© 2026 Tane Channel Technology」（pic2gray4px と同形式）。
- 利用部品は、再配布と商用利用が可能なライセンスのものに限る（MIT／BSD／Apache-2.0 等の許諾型、および分離して使う LGPL の Codec2）。QR 生成は Nayuki の QR Code generator（MIT）、QR 読取は zxing 系（zxing-cpp は Apache-2.0、zxing-wasm は MIT）を採用する。
- バージョン表記はセマンティックバージョニング（大規模改定でメジャー、機能改定でマイナー、バグ修正でパッチ）。開発中は 0.x 系とし、初版リリースを 1.0.0 とする。
- Android の署名は Play App Signing を使う（フェーズ2）。GitHub 配布の APK は自分の署名キーで署名し、そのキーを将来のアップロードキーとして保管する。署名キーは本人の PC で生成し、本人がローカル管理する（VM には置かない）。
- CI ではゴールデンテスト（§7 のフィクスチャとのバイト単位の照合）を必須とする。
- Codec2 は **LGPL-2.1** の別コンポーネント。**無改造**で、動的リンク／別ライブラリ（Android では別 .so）として利用する。自前コードに取り込まない。Codec2 の COPYING（LGPL-2.1 本文）と帰属表示を同梱する。静的リンクで単一バイナリに一体化しないこと（LGPL の再リンク可能性の条件を避けるため）。Codec2 自体を改造した場合は、その部分は LGPL で公開が必要。
- その他の部品： segno（BSD）、zxing-cpp（Apache-2.0）など寛容ライセンスのみ。
- 名称は「Voice2QR」に決定（2026-11-14）。当初案「QRvox」は同名の既存アプリと衝突するため不採用。「紙声 Kamigoe」も候補に挙がったが、国際的に伝わらないため見送った。X2Y 表記は自身の pic2gray4px と同じ命名の系譜。データフォーマット名とマジック「QV」は、検証フィクスチャとの互換性のため変更しない。
- 開発分担： 開発は Muse が専用の VM で行う。VM から git コマンドでの直接 push はできないが、GitHub コネクタの push 機能でコードと文書（テキストファイル）を tanep3/Voice2QR へ反映できる（1回ごとに Tane の承認。ファイルの削除はこの経路では扱えない）。バイナリや画像は送れないため、成果物（APK 等）は GitHub Actions（CI）で生成し、README のサンプル QR 画像のような単発のバイナリは Tane が手で追加する。前提（完了）： Tane が tanep3/Voice2QR を作成し、Muse の GitHub App の対象に追加済み（2026-11-14）。初回 push（ライセンス一式・README・QV フォーマット仕様・スパイク一式）も同日完了。資料の正本は本ファイル（`docs/requirements.md`）。Notion のコピーは閲覧用、Google Drive「ChatGPT/Voice2QR」のミラーは補助（仕様共有用）。

# 7. 実証済み（2026-11-14 スパイク）

Muse の VM で方式検証を完了。パイプライン全通：

- サンプル音声（VOICEVOX 波音リツ、8.64秒、8 kHz モノラル）→ Codec2 符号化 → QR 生成 → 生成画像を読み戻して **バイト列完全一致** → 復号した PCM も **完全一致**。Tane が聴取し「しっかりと聞き取れる」と確認。
- 実測値（1200 bps）： ペイロード 1,303バイト（音声 1,296＋ヘッダ7）→ QR バージョン30（訂正 M）。10秒の場合はバージョン32。（いずれも v1 形式での実測。v2 では同一音声で 1,306バイトとなり、バージョン30のまま収まる。）
- 参考（2400 bps）： 同音声で 2,599バイト → バージョン38（訂正 L）。訂正 M では収まらない。
- スパイクのコードは本リポジトリ `spike/` にある。検証フィクスチャのバイナリ実物（原音声、QR 画像、復号音声、比較画像）は Muse の VM が正本で、`fixtures/` には説明のみを置く。実装の照合（ゴールデンテスト）に使える。
